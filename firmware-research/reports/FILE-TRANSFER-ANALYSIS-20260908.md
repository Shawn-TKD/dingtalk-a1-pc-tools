# A1 V1.6.88 file-transfer reconstruction\n\nThis note separates three different mechanisms that the stock firmware calls\n"file transfer". They are not interchangeable.\n\n## 1. Ordinary recording list and synchronization\n\nBLE commands `0x0110` through `0x0115` operate on indexed recordings under\n`/emmc/audio`.\n\n- `0x0110` requires a connected DID, decimal-string `s_fid` and `e_fid`, and an\n  optional numeric `recently` in `1..300`.\n- Peers advertising SDK support at least 1.6.88 may list normally. A legacy peer\n  is allowed only when `persist.dt.aud.force_sync` was read successfully as one.\n  Incognito mode and `persist.dt.aud.incognito_flag` otherwise select only the\n  diagnostic denial reason; they do not create another allow path.\n- The binary response begins with big-endian `code:u16` and `count:u16`, followed\n  by `count` eight-byte entries: `flag:u16`, `fid:u32`, and an opaque 16-bit\n  status/duration hint.\n- Stock always appends `00 00 00 <truncated> 5a 5a 5a 5a`. The truncation byte is\n  one when `recently` shortened the result or the internal 300-entry cap was hit.\n- `0x0111` takes decimal-string `fid`, numeric `offset`, and numeric `progress`.\n  The selected file is `/emmc/audio/%014llu`. Offset equal to file size returns\n  stock code 100 (nothing left); setup failures map to 201..203. Synchronization\n  is rejected with `0x0199` while the audio state is neither idle nor paused.\n- The device sends `0x0114` JSON attributes with decimal `fid`, `size`, and an\n  `attrs` string. Ordinary files use `audio@opus@...`; FID zero uses\n  `voice@opus@...`.\n- Each `0x0115` body is big-endian `reserved:u16 | fid:u32 | reserved:u16 |\n  sequence:u32 | length:u32 | data | reserved:u32 | crc:u32`. The stock read\n  slice is 48,000 bytes, and the CRC is CRC-32/BZIP2 over `data`.\n- A code-200 response advances the stream. Any other block response requests a\n  resend; the ordinary transfer path preserves and caps the retry count at three.\n- `0x0112` cancels asynchronously. `0x0113` sends the success response before\n  queueing database and `/emmc/audio/%014llu` deletion, so a received 200 is not\n  durable proof that deletion completed.\n\nThe main workers are `0x103e1230`, `0x103e1374`, `0x103e1688`, `0x103e17b0`,\n`0x103e19fc`, and `0x103e1a78`. Queue wrappers live at `0x103e1bf4` through\n`0x103e2280`; the transfer event reducer is `0x103e2750`.\n\n## 2. Raw known-path BLE read\n\nCommands `0x014A`, `0x014B`, and `0x014C` form a second, simpler, read-only\nprotocol.\n\n- `0x014A` requires DID, UTF-8 `path` (copied into a 64-byte buffer), and optional\n  nonnegative `offset`.\n- The firmware opens the requested path as `rb`; there is no directory-list\n  operation in this command family.\n- The response contains `code`, `path`, `size`, `offset`, `block_size=8000`,\n  `total_blocks=ceil(size/8000)`, and `remain_blocks`.\n- File-not-found and invalid-offset JSON responses use codes 404 and 502.\n- A `0x014B` body is `sequence:u32 | length:u32 | data | crc:u32`, big-endian,\n  with CRC-32/BZIP2. Sequence numbering begins at one.\n- The peer answers code 200 to advance or `0x0193` for CRC failure. The stock raw\n  resend worker increments a three-attempt counter, but the common send worker\n  resets that counter again, so repeated CRC failures can loop indefinitely.\n  The compatible implementation deliberately keeps the count and aborts after\n  three consecutive failures.\n- `0x014C` sets a cancellation flag, closes the file, releases its buffer, and\n  responds 200.\n\n`dingtalk-a1-sdk` now implements this as\n`client.experimental.download_raw_file()`. It restricts public reads to known\n`/emmc` paths, streams to `.part`, validates every CRC, and supports exact-offset\nresume. This is host-tested against a protocol peer but remains hardware-static\nuntil repeated on the owner's A1.\n\n## 3. Device-bound uploads\n\nThe request handlers at `0x103cbb78` and `0x103cbe58` receive data *into* the A1,\nbut they are not a general-purpose filesystem writer.\n\n- `attrs=ota@bin` enters the OTA receiver and additionally requires the version\n  query/update preconditions.\n- The only other accepted prefix is `image@bmp@usrinfo...`; it writes\n  `/emmc/usrinfo.tmp`, verifies the completed file, and publishes it as\n  `/emmc/usrinfo.bmp`.\n- The header carries numeric `size`, string `verify_code`, string `attrs`, and an\n  OTA-only `version`. The firmware hashes the verify-code string for later\n  comparison with the hash of the computed 32-character file digest.\n- Incoming binary blocks contain big-endian type/reserved, CRC, sequence, and\n  length fields before the data. CRC failure returns `0x0193`.\n\nTherefore this path is useful for reconstructing OTA and user-image behavior,\nbut it is not evidence that arbitrary videos or documents can be written by BLE.\nThe already verified USB/ADB `/emmc/mindlink` adapter remains the safe general\nfile-storage route.\n\n## Compatible-source coverage\n\n`compat-src/src/file_sync.c` now provides:\n\n- exact stock list encode/decode including the truncation trailer;\n- legacy/incognito permission decisions;\n- ordinary block encode/decode with trailer CRC verification;\n- duplicate/order/size validation on the receiving side;\n- a 48,000-byte, three-retry ordinary sending state machine.\n\n`compat-src/src/raw_transfer.c` provides the 8,000-byte raw block codec and\nbounded sender state. Platform adapters, the recording database, filesystem I/O,\nand the asynchronous BLE queue remain explicit target-HAL work rather than being\nhidden inside host codecs.\n\n
