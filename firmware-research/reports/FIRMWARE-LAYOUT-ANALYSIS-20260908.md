# DingTalk A1 V1.6.88 Flash、启动与多核装载布局

本页记录能够由固件字节、反编译调用链和机主设备只读回读共同验证的布局。
地址只用于解释原厂 V1.6.88，不能被兼容源码当成可调用的固定 ABI。

## 16 MiB NOR Flash 分区表

AP 的 `bes_partition_init`（`0x1026f1c8`）循环注册 12 个静态表项。表位于
`0x10497fd4`，每项 `0x74` 字节；名称从项首开始，`+0x68` 为起始块，
`+0x6c` 为块数，块大小是 `0x100` 字节。换算后的完整几何如下：

| 名称 | Flash 偏移 | 长度 | 结束位置 | 实机节点 |
| --- | ---: | ---: | ---: | --- |
| `ota_b` | `0x00040000` | `0x000a0000` | `0x000e0000` | `/dev/ota_b` |
| `ota` | `0x000e0000` | `0x000a0000` | `0x00180000` | `/dev/ota` |
| `ota_info` | `0x00180000` | `0x00008000` | `0x00188000` | `/dev/ota_info` |
| `ota_flag` | `0x00188000` | `0x00008000` | `0x00190000` | `/dev/ota_flag` |
| `ap` | `0x00190000` | `0x00800000` | `0x00990000` | `/dev/ap` |
| `apc1` | `0x00990000` | `0x00300000` | `0x00c90000` | `/dev/apc1` |
| `hifi` | `0x00c90000` | `0x00170000` | `0x00e00000` | `/dev/hifi` |
| `user` | `0x00e00000` | `0x00100000` | `0x00f00000` | `/dev/user` |
| `misc` | `0x00fe2000` | `0x00001000` | `0x00fe3000` | `/dev/misc` |
| `bootinfo` | `0x00fe3000` | `0x00001000` | `0x00fe4000` | `/dev/bootinfo` |
| `bes_reserved` | `0x00fe4000` | `0x0001b000` | `0x00fff000` | `/dev/bes_reserved` |
| `factory` | `0x00fff000` | `0x00001000` | `0x01000000` | `/dev/factory` |

设备报告的物理 Flash 大小和 AP 构建字符串均为 `0x01000000`。表中没有注册
`0x00000000..0x0003ffff` 以及 `0x00f00000..0x00fe1fff`；这不代表两段为空，
前者尤其可能包含原厂启动链。兼容实现不能占用这些空洞。

实机只读结果分别给出 AP 8 MiB、APC1 3 MiB、HiFi `0x170000` 和 USER
1 MiB，逐项验证了静态表的换算。`compat-src` 的 `flash_layout` 模块把这张表
建模为只读描述符，并检查越界和重叠，不提供擦写函数。

## 镜像头和已安装标记

OTA ZIP 中 AP/APC1 的首字为 `0xffffffff`；机主设备的相同分区首字为小端
`0xbe57ec1c`，其余 OTA 镜像长度内仅这四个字节不同。因此首字是安装流程
写入或提交的启动有效标记，而不是普通程序数据。HiFi 和 USER 的 OTA 前缀
与实机完全相同。

这意味着把 ZIP 中的 `nuttx_ap.bin` 原样写入 `/dev/ap` 并不等价于一次合法
安装。谁在何时校验包、写有效标记、失败时如何回退，仍属于启动/升级链的
未恢复部分。

## AP 和 APC1 启动内存

AP 的原厂 Flash 映射起点为缓存地址 `0x10190000`，非缓存别名为
`0x30190000`。入口跳板在镜像 `+0x10`，装载 `0x10190015`：

- MSP：`0x203bffe0`；MSPLIM：`0x203bf3e0`；
- 初始化数据：`0x1053abc0` 复制到
  `0x201d16f0..0x201dcd73`，长度 `0xb684`；
- BSS：`0x201dcd74..0x20275a2b` 清零；
- 随后进入 `0x10259388`，继续 NuttX/板级启动。

`0x10190090` 在启动早期于 SRAM `0x201c0000` 建立 136 项向量表，并把
VTOR 指向该表。前 16 项来自 `0x10195b70`，其余项初始统一指向
`0x10190085`；外设驱动随后在运行期安装 IRQ。因此向量表的创建方式已经
恢复，尚缺的是各 BSP 驱动最终注册的 IRQ、优先级和安全域归属清单。

APC1 分区的入口跳板同样位于镜像 `+0x10`，跳到 `0x10a9b8fd`：

- MSP：`0x201bffa0`；MSPLIM：`0x201bf7a0`；
- 初始化数据：`0x10c2ce44` 复制到
  `0x200e7c68..0x200eb20f`；
- BSS：`0x200eb210..0x201445df` 清零；
- 随后进入 `0x10aceabc`。

这些值足以为未来 linker script 建立证据约束，但还不足以生成可启动镜像：
运行期 IRQ 归属、TrustZone/MPU 设置、ROM 调用和 BES BSP 初始化仍要恢复
或由匹配的厂商 SDK 提供。

## AP 启动其他处理核

AP 中可以区分三条子系统启动链：

| 子系统 | 原厂描述符/镜像地址 | 关键函数 | 后续通道 |
| --- | ---: | ---: | --- |
| HiFi4 DSP | `0x30c90000` | `0x10232354` | `M55C0_2_DSPC0`、`dsp_hifi4_ipc_open` |
| Bluetooth host core | `0x28000000` | `0x1022c4a8` | `M55C0_2_BTHC0`、`bt_host_open` |
| M55 core 1 / APC1 | `0x30990000` | `0x1023388c` | `M55C0_2_M55C1`、`cp_subsys_open` |

通用子系统检查函数 `0x10231e6c` 要求描述符首字为 `0xbe57ec1c`，成功时把
`descriptor + 0x10` 作为启动入口。APC1 的安装后首字正好满足该检查。

HiFi 头在文件 `+0x08` 处带相同 magic，并明确给出入口 `0x100cd150`、
IRAM `0x00880000..0x00900000`、DRAM `0x20880000..0x209c0000`。函数
`0x10232354` 还遍历其复制表，将 Flash/PSRAM 中的段复制进 DSP 地址空间。
USER 镜像更像 HiFi/SMF 动态算法载荷；它的专有重定位格式尚未完整恢复，
不能假定是第四个可独立启动的 NuttX 核。

## 对兼容实现的直接意义

1. 可以准确限制四个程序镜像的最大尺寸，并生成不会越过相邻分区的链接
   产物。
2. 可以在不改伴随核镜像的阶段，优先尝试“自有 AP + 原厂 APC1/HiFi/USER”
   的兼容策略；前提仍是恢复 AP 侧 RPTUN/OpenAMP 资源表和 BSP ABI。
3. 可以把系统状态、升级状态和工厂身份区域从普通设置/录音存储中分离，
   避免兼容代码误擦除。设备专属秘密的完整落点尚未由这张表单独证明。
4. 目前仍不能安全刷写：BootROM、包验签、有效标记提交、故障回退和 ROM
   恢复入口没有闭环。下一步应先完成启动链只读回读和 no-flash 链接验证。

AP 侧 RPTUN ops 表、BES `rmt_ipc` core/channel/resource ID、三块本地
vring arena 及 M55C1 共享资源表的后续恢复见
`RPTUN-ABI-ANALYSIS-20260908.md`。
