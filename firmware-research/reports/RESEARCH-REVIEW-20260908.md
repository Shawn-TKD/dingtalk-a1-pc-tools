# A1 固件研究复核：已有成果、纠正与下一阶段

## 2. 纠正：命令表的四个字段顺序

此前读取静态表时把前一个条目的函数指针和下一个条目的名字配到一起，导致部分口头说明发生错位。原始字节显示实际 16 字节条目为：

```text
name_pointer | priority | stack_size | entry_pointer
```

| 命令 | 条目起点 | 处理函数（去掉 Thumb 位） | 静态行为 |

| `lnv_key_status` | `0x104a25d4` | `0x1030baa8` | 读取两个按键状态 |

| `lnv_os_test` | `0x104a2624` | `0x1030cc2c` | 包含 SN/MAC、DTIOT 读写、恢复及升级等子命令 |

| `lnv_wifi_ap_create` | `0x104a2674` | `0x1030e0ec` | 创建 AP |

运行记录中的 `help` 已确认这些名字存在。功能描述来自静态控制流，不代表本轮执行过所有命令。`lnv_os_test all` 包含写配置的测试，不能用来做只读诊断。

`lnv_os_test flash_read` 的单次长度限制是 1–1024 字节；下层 `dtiot_hal_os_flash_read/write` 的整个地址范围被限制为 `0..0xffff`，且偏移与长度之和不得超过 `0x10000`。地址属于 DTIOT 逻辑配置区，并非整颗 Flash 的物理地址。

因此这个入口可帮助研究身份配置，但不能替代 `/dev/bes_flash` 的完整备份。`factory_section` 日志名也不能直接等同于 4096 字节的 `/dev/factory` 节点；DTIOT 的物理映射仍须单独确认。

## 3. 纠正：原始秘密与客户端认证字符串分为两层

固件的生成函数产生 16 字节原始秘密 R，并经 `0x103cf5d8` 写入 DTIOT 偏移 `0x0000` 的 64 字节槽。不能把这 16 字节直接当作客户端应填入的字符串。

`dt_get_device_secret_md5`、`dtiot_ble_generate_token_hash` 和 `dtiot_hid_generate_token_hash` 都显示如下转换：

```text
R：设备保存的原始 16 字节
H：R 的小写十六进制表示，共 32 个 ASCII 字符
S：MD5(ASCII(H)) 的小写十六进制表示，共 32 个字符
认证 key = IV = ASCII(S 的前 16 个字符)
token = AES-128-CBC(key, IV, ASCII(challenge)).hex()
```

固件调试信息将 S 显示为 `devSec`。此前已验证的电脑客户端以缓存 `deviceSecret[:16]` 的 ASCII 字节作 key/IV，与这条链中 S 的角色相符。尚未直接取得这台设备 DTIOT 中的 R 并与其缓存值作逐项比较，因此不把本轮称为已经从设备重新提取了当前密钥。

初始化读取偏移 `0x0300` 的绑定状态；未绑定时走生成路径，已绑定时读取旧秘密。解绑函数清零 `0x0000/0x0100/0x0200/0x0300/0x0500` 各槽。后续进入未绑定初始化路径时会重新生成原始材料。由此可以判断：身份材料并非不可变的出厂常量；普通升级是否保留，取决于配置区与绑定状态是否保留。

随机包装 `0x103c8638` 逐字节调用 `0x1026849c`；其播种及熵来源没有完整还原。本轮没有得到从 SN/DID/corpId 推算现有秘密的方法。

证据：`decompiled/focus/103cf954_dtiot_device_generate_and_set_secret.c`、`103cf9e8_dtiot_product_info_check.c`、`103cf6c4_dtiot_device_unbind.c`、`103c3cd8_dt_get_device_secret_md5.c`、`103ca86c_dtiot_ble_generate_token_hash.c`、`103e3214_dtiot_hid_generate_token_hash.c`、`103c3f08_dt_dbgserial.c`。

## 4. 升级链仍有两个实质缺口

应用层 OTA 接收链已恢复：接收 ZIP、校验传输内容、保存到 `/emmc/ota.zip`，随后进入升级启动模式。完整的验签策略、分区刷写流程和失败恢复入口尚未定位。

不能仅因在当前字符串或函数搜索中没有找到验签代码，就断言它绝对不在四个镜像中。独立 `/dev/ota`、`/dev/ota_b` 及启动区域是优先分析对象；需要实际导出后验证。

此外，原始 `ota.sh` 的进度监控存在特殊行为：

- 进度连续停滞超过阈值时，脚本会主动把 `/emmc/ota_progress` 增加 1；
- 总超时后，如果进度已经达到 95 或以上，会写入 100；
- 部分最终成功判断依据该进度文件。

因此进度达到 100 或打印 SUCCESS，本身不足以证明镜像已正确刷入。未来验证自定义固件，需要结合实际写入结果、重新启动及读回内容判断。此结论来自脚本原文，尚未触发 OTA 实验。

## 5. 对产品开发的意义与下一步

现有成果足以继续开发设备外的 Agent 输入、备忘录自动同步、录音时间轴标记和 Wi-Fi 加速传输；这些功能的协议实现与实测进度须分别记录。

独立蓝牙震动、任意屏幕内容、自定义按键状态机目前还没有验证过的外部入口。原始固件存在相关内部模块；修改它们之前，最有价值的是先恢复升级及回退路径。

下一阶段顺序：

1. 在设备可访问时只读导出完整 16 MiB Flash 和独立 OTA/启动/配置区域，确认分区物理位置及备份可解析性。
2. 在 AP 中补齐关键间接调用、正确原型及少量可读伪代码，优先围绕按键 → 音频 → 状态反馈；避免用函数数量替代语义验证。
3. 用已知正常的身份与报文验证 BLE 原始文件读、Wi-Fi 下载、标记 ACK 及显示状态，逐项补充实机证据。
4. 根据启动与验签结果设计最小的反馈扩展；具备恢复证据后再进入刷写实验。
5. DSP/USER 先解决 HiFi4 指令和动态装载支持，再研究音频算法内部实现。

本轮静态复核未重新连接实机。上一轮枚举没有发现 A1 HID，ADB 列表为空；这是当时的观察，不能代表用户之后的连接状态。
